# Memory management (operating systems)

In an operating system, **memory management** is the function that controls the computer's primary memory, the working RAM directly addressed by the CPU. It tracks every memory location as allocated or free, decides which running processes get memory, when they get it, and how much, and picks which locations to assign when a process is granted memory. This is separate from *application memory management*, which is how a single process manages the memory the OS has already handed it.

The central problem the function solves is straightforward: multiple processes want to share one finite bank of RAM safely and efficiently. Each technique below is a different answer.

## The core techniques

**Single contiguous allocation.** The simplest approach: hand nearly all RAM to one application, leaving a small slice for the OS. MS-DOS worked this way, as do many embedded systems that run a single program. Multitasking is still possible by swapping the whole application out to disk to let another user run.

**Partitioned allocation.** Memory is split into several contiguous regions called *partitions*, each holding one job or task. Memory management then becomes bookkeeping: assign a partition when a job starts, reclaim it when it ends. Partitions can be *static* (fixed at boot, as in IBM's MFT) or *dynamic* (created on demand, as in IBM's MVT, which calls them *regions*). Static partitions waste space when jobs are small; dynamic partitions leave gaps when jobs of different sizes end. Compaction slides the live partitions together to close those gaps, but requires relocation hardware such as *base and bounds* registers (used on the UNIVAC 1108, PDP-6, PDP-10, and GE-600 series) that let a program be moved without rewriting its code. The IBM System/360 instead used a *lock-and-key* scheme to keep jobs from interfering with each other. A partition can also be swapped to secondary storage to free more RAM; early IBM TSO swapped time-sharing users in and out this way.

**Paged memory management.** Memory is divided into fixed-size *page frames*, while each program sees its own virtual address space split into same-size *pages*. A hardware *memory management unit* (MMU) translates page numbers into frame numbers on every memory access. The physical RAM backing a program becomes scattered across frames, but the program experiences one contiguous address space. Most systems give each process a private address space; a few *single address space operating systems* (IBM i, OS/VS1, OS/VS2 SVS) map every job into one shared 16 MiB virtual address space instead. Pages can be moved between RAM and disk on demand, which is what most readers know as *virtual memory*.

**Segmented memory management.** Memory is organised around *segments*, variable-sized regions that usually match a logical unit of the program: a procedure, a data array, a stack. A segment table in hardware holds each segment's physical base address, length, and access-protection bits. Because every memory reference names a specific segment and an offset within it, the hardware can refuse any access outside that segment, giving stronger access protection than paging or partitions. A segmented address is normally a *segment id* plus an *offset from the segment base*. Segmentation can run without paging (the whole segment is swapped), or be layered on top of paging (pages inside segments are swapped, and segmentation adds an extra authorisation check). On IA-32 (x86), a process may have up to 16,383 segments of up to 4 GiB each, and segments are subdivisions of the linear address space created by the paging hardware. Multics is the classic example: segments were subdivisions of physical memory of up to 256 pages of 1 K 36-bit words, giving a 1 MiB maximum segment size, with up to 4046 segments per process.

**Rollout/rollin (RO/RI).** A whole program's non-shared code and data is copied to auxiliary storage (disk or drum) so another job can use main memory. The trigger is usually a long wait, such as user "think time" in a time-sharing session. RO/RI needs no MMU, but without relocation hardware the program must return to the same addresses it left. It was an optional feature of OS/360 MVT and has been largely superseded by paging. RO/RI also let a job temporarily expand beyond its own region by borrowing space, then rolling the displaced job back out; in OS/360 this only applied to batch jobs, and rollin did not happen until the borrowing jobstep finished.

## What the choices trade off

The techniques sit on a spectrum. Single contiguous allocation is simplest but can run only one program at a time without swapping. Partitioned allocation adds hardware protection and lets several jobs coexist, but static partitions waste space and dynamic ones fragment it; compaction and swap-out recover some of that waste at the cost of relocation hardware or I/O. Paging eliminates external fragmentation by scattering a process across many small frames, and demand paging extends RAM cheaply with disk, but it requires an MMU. Segmentation trades the uniform page size for memory that matches the program's logical structure and gives finer access control, at the cost of a more complex address translation and, without paging, the same fragmentation problems as partitions. Rollout/rollin is the crude predecessor of demand paging: it swaps whole programs instead of individual pages, so it works without special hardware but is much coarser-grained.

Four jobs keep reappearing under different names: track which memory is free, allocate it to a process, protect one process from another, and extend the effective size of RAM by spilling less-used contents to secondary storage. Single contiguous allocation does the first two only; partitions add protection; paging and segmentation add fine-grained protection plus virtual address spaces large enough to overflow physical RAM.
