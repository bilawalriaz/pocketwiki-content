# Scripting language

A scripting language is a programming language used to write scripts: short programs that automate work a person would otherwise do by hand, such as running a sequence of shell commands, transforming a batch of files, or driving an application through its menus. Writing such a program is called scripting. The term is fuzzy: it covers a spectrum from tiny shell one-liners to large programs, and a language may shift along that spectrum over time.

The word "script" originally meant the short programs fed to interactive operating-system shells in the 1960s. From those roots the meaning broadened. Today a scripting language may be a general-purpose language (Python, Ruby, Perl, JavaScript), an extension language embedded inside another application (Lua in game engines, VBA in Microsoft Office, Emacs Lisp in Emacs), a job-control or shell language (Bash, KornShell, PowerShell, IBM's JCL), or a GUI automation language that simulates clicks and keystrokes. A macro language is a related case where control happens through simulated input.

Several properties are typical, though none is a hard rule. A script is usually interpreted directly from source or from bytecode, sometimes after just-in-time compilation, rather than built ahead of time into a standalone executable. It is usually short, often fits in a single file, and rarely exceeds a few thousand lines. It usually automates a manual task, so it begins executing at its first line, unlike a traditional application that starts at a designated entry point such as Java's `main` function. And it is typically written or modified by the person running it, though scripts are also distributed, as with the game logic shipped inside Google Chrome's T-rex game.

These traits place scripting languages in contrast with systems programming. John Ousterhout framed the difference as "programming in the large versus programming in the small." A scripting language used this way is called a glue language: it connects existing software components rather than implementing low-level algorithms from scratch. Pipelines and shell scripts are the archetypal glue. Web development often uses glue languages too, sitting between a database and a web server, though when the script grows into a substantial component of its own it stops being mere glue.

The historical path explains why so many scripting languages exist. Early mainframe computers ran jobs in batches; IBM's Job Control Language (JCL), documented from 1967, was the archetype for telling the system what to run. The first interactive shells appeared in the 1960s on time-sharing systems, and Louis Pouzin's RUNCOM for CTSS (around 1964) and Stuart Madnick's EXEC for IBM's CP/CMS (1966) were early command-script processors; EXEC later evolved into EXEC 2 and Rexx. Calvin Mooers' TRAC language is credited with inventing command substitution, the ability to embed commands inside scripts so the interpreter splices their output back into the text; Multics called the same idea active functions.

Two later shifts reshaped the field. First, languages such as Tcl and Lua were designed from the start as embeddable scripting engines that any C-based application could host, sparing each program the cost of inventing its own language. Second, JavaScript, originally confined to web browsers, was standardized as ECMAScript and is now embedded in many non-browser environments, from the Mozilla SpiderMonkey engine used in Adobe's Flash and Acrobat to server-side runtimes. Perl shows the opposite migration: it began as a text-processing and glue tool and grew into a general-purpose language, with the Oraperl dialect (1990) later replaced by the DBD::Oracle library.

Modern applications often expose a scripting interface so users can extend them. Autodesk Maya embeds the Maya Embedded Language; Blender uses Python. Game engines favour Lua or Python for fast iteration, since designers can tweak behaviour without rebuilding the engine, and the Chrome T-rex game is a familiar example of game logic written entirely in script. Some scripting languages are tied to a single application: TrainzScript in Trainz, the Linden Scripting Language in Second Life, QuakeC in Quake. These can be read as domain-specific languages specialised to one program.

The boundary between a script and a full application blurs at the edges. Java, C, and Visual Basic are general-purpose languages that can be used to write scripts through tools such as JBang or Tiny C Compiler, while Python and JavaScript are routinely used for both small automations and large systems. What marks a script is less the language than the use: a short program, often interpreted, that automates an otherwise manual task, written to be read and changed by the people who run it.
