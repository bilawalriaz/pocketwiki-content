# Computer architecture

A computer architecture is the abstract design of a computer system: how its parts are organised, how they interact, and what rules govern the flow of data and control. It is not the concrete hardware. Two machines built from different transistors can share one architecture, because architecture describes capabilities and the programmer's contract, not the wiring.

The discipline divides into three layers. The **instruction set architecture (ISA)** is the contract between software and hardware: the machine code a processor reads, along with the word size, registers, addressing modes, and data types. A processor only understands numerical instructions; compilers and assemblers translate languages like C and Java into the ISA's encoding. The ISA is what a small instruction manual documents and what an assembler turns into machine-readable form. **Microarchitecture** (also called computer organisation) is how a particular chip implements that ISA. Cache sizes, pipeline depth, and the arrangement of functional units are microarchitectural choices the ISA need not reveal. **Systems design** covers everything else: memory hierarchies, direct memory access, multiprocessing, and I/O. Two facts make this split useful. One ISA can be implemented by many microarchitectures with different performance and cost. Hardware features outside the CPU, such as virtual memory, are system-design concerns that matter to software even though they sit below the ISA.

A good ISA balances competing pressures. Rich instructions let a single opcode express a high-level operation and shrink programs; the x86 `LOOP` instruction is a classic example. Complex instructions are slower to decode, cost more silicon, and create more chances for subtle bugs when instructions interact unexpectedly. ISA quality is judged on four axes at once: code readability, code size, hardware cost to decode, and execution speed. Designers test these tradeoffs in emulators that measure size, cost, and speed before silicon is fabricated.

Once an ISA and microarchitecture are fixed, **implementation** turns the design into hardware. The chain runs from logic gates through transistor-level circuits to a physical floorplan of wires and components, ending with prototype testing on FPGAs and then on real chips. Hobby projects usually stop at the FPGA stage; commercial CPUs iterate through several redesigned prototypes.

Design goals are constrained tradeoffs among performance, cost, power, reliability, memory capacity, latency, and throughput. **Latency** is the time from starting a task to finishing it; **throughput** is work done per unit time. Pipelining often worsens latency for a single instruction while raising throughput overall. **Instructions per cycle (IPC)** is the standard efficiency measure: older machines reached as low as 0.1 IPC, modern designs approach 1, and superscalar chips that issue several instructions per clock reach three to five. Clock rate alone is a misleading indicator, because a slower-clocked chip with higher IPC can outperform a faster-clocked one, and manufacturers now report performance per second or per watt rather than gigahertz. Benchmark suites measure real behaviour but favour specific workloads, so a chip that tops one benchmark may trail on unrelated tasks. Real-time systems, such as anti-lock brake controllers, add a hard constraint: an interrupt must be serviced within a guaranteed maximum time, or the system fails.

**Power efficiency** has become as central as raw speed. The historical measure was MIPS per watt; modern designs use performance-per-watt and energy-per-instruction. Per-transistor energy use has improved, but total chip power has risen because transistor counts keep growing, demanding complex power delivery and raising power density. Hotter chips suffer higher interconnect resistance, which increases power draw and heat in a feedback loop. As transistor scaling has slowed, the industry has shifted from chasing clock speed and transistor count to chasing efficiency. Intel's Haswell microarchitecture illustrated the move, dropping its power-consumption benchmark from 30–40 W to 10–20 W. Mobile and embedded devices, where battery life and thermal limits dominate, drove the same shift earlier and harder.

The term has a specific history. The first documented architecture appears in Charles Babbage and Ada Lovelace's notes on the analytical engine. In 1936, Konrad Zuse filed patents describing the stored-program idea: instructions and data share one memory. John von Neumann's 1945 EDVAC report and Alan Turing's 1945 ACE proposal formalised the organisation of logical elements. The word "architecture" entered computing vocabulary in 1959, when Lyle Johnson, writing about IBM's Stretch supercomputer, used "system architecture" to describe the right level of abstraction. Frederick Brooks then defined computer architecture as "the art of determining the needs of the user of a structure and then designing to meet those needs as effectively as possible within economic and technological constraints." Brooks carried the term into the IBM System/360 line, where "architecture" became a noun for "what the user needs to know," a usage that persists in today's IBM Z mainframes. Earlier designs were drawn on paper and built directly; transistor–transistor-logic prototypes for chips like the 6800 and PA-RISC came next; since the 1990s, new architectures are typically simulated in software or compiled into FPGAs before silicon is committed.
