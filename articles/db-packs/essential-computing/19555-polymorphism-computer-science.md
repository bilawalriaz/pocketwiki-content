# Polymorphism (computer science)

In programming language theory, **polymorphism** lets a single value, variable, or operation work across more than one type. In object-oriented programming, it usually means providing one interface to entities of different data types. The name is borrowed from biology, where an organism can take several forms. The most commonly recognised forms are ad hoc polymorphism, parametric polymorphism, and subtyping.

## Three main forms

**Ad hoc polymorphism** applies one function name to arguments of different types, with different behaviour per type. Christopher Strachey coined the label "ad hoc" because the polymorphism is not a fundamental property of the type system; it is supplied case by case. The usual instances are function overloading and operator overloading. A compiler treats each overloaded function as a distinct routine even though the source looks unified. Implicit type conversion has also been called "coercion polymorphism". Strachey described this kind, and parametric polymorphism, as the two main classes of polymorphism in *Fundamental Concepts in Programming Languages*. Ad hoc polymorphism was a feature of ALGOL 68.

**Parametric polymorphism** writes a function or data type so that it handles values uniformly, without committing to a concrete type. A type variable stands for any type. A function that can be applied to values of different types is a polymorphic function; a data type parameterised over its elements, such as a list of arbitrary element type, is a polymorphic data type. The mechanism preserves full static type safety because the same code is reused for every type. It is ubiquitous in functional languages, often simply called "polymorphism", and is the core feature of ML's type system. It also appears as C++ and D templates, and as generics in C#, Delphi, Java, and Go. John C. Reynolds, and later Jean-Yves Girard, formalised it as System F, the polymorphic lambda calculus. A side effect is *parametricity*: a parametrically polymorphic function can only depend on the shape of the data, not on any value-specific property.

**Subtyping**, also called subtype polymorphism or inclusion polymorphism, restricts the range of acceptable types by a type hierarchy. A function written for a type T also accepts any subtype S, by the Liskov substitution principle, written `S <: T` ("S is a subtype of T"), with `T :> S` for the converse. Peter Wegner and Luca Cardelli introduced the term "inclusion polymorphism" in a 1985 paper, citing Simula as the first language to implement it. In typical object-oriented implementations, subtype polymorphism is resolved dynamically: each class carries a *virtual table* (vtable) of polymorphic methods, each object carries a pointer to its class's vtable, and calls are looked up through that pointer at run time. This is late binding and *single dispatch*, because the runtime type of the receiver (the `this` object) chooses the method while the other arguments' types are irrelevant. Some object systems, such as the Common Lisp Object System, generalise this to *multiple dispatch* over all arguments. Combining parametric polymorphism with subtyping gives type variance and bounded quantification.

## Related forms

*Row polymorphism* works on structural types and accepts values whose types share certain fields while keeping the rest of the type information intact; it is distinct from subtyping. *Polytypism* (or data type genericity) generalises further: a polytypic function is parameterised over the structure of a type itself rather than over a type variable. *Rank polymorphism* treats every operation as an aggregate operation usable on arrays of arbitrarily many dimensions, a defining feature of array languages such as APL.

## Static versus dynamic

Polymorphism can also be classified by when the implementation is chosen. *Static polymorphism* (static dispatch) selects the code at compile time, runs faster, and gives compilers and readers more information for optimisation; it is the typical form for ad hoc and parametric polymorphism. *Dynamic polymorphism* (dynamic dispatch) selects the code at run time, usually through a virtual function call, and is more flexible: it enables duck typing, and a dynamically linked library can operate on objects without knowing their full type. Subtype polymorphism is usually dynamic, although static polymorphism with subtyping is possible through template metaprogramming patterns such as the curiously recurring template pattern. Static polymorphism cannot cross dynamic-library boundaries when the parameter types are not known when the shared object is built; C++ and Rust monomorphise templates per call site, while Swift uses dynamic dispatch for its application binary interface, trading runtime overhead for smaller, shareable binaries.
