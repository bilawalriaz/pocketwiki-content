# Tokenization (data security)

Tokenization is the substitution of a sensitive data element with a non-sensitive equivalent, called a token, that has no exploitable meaning on its own. The token is merely an identifier pointing back to the original data through a tokenization system. Tokens are typically produced from random numbers or one-way cryptographic functions, making the original value infeasible to recover without access to the system's resources. The system stores the actual sensitive data in a vault database and is the only component that can map tokens back to their live values, which is why the vault must be strongly protected and isolated from other systems.

A token is not encryption. Encryption is a mathematical, reversible transformation that alters the type and length of data, which can break legacy databases and intermediate systems. Tokenization is a non-mathematical swap that preserves format and length, so a token can stand in for a primary account number (PAN) without breaking processing pipelines. Tokens require far less computation, and a properly designed token reveals nothing useful even if intercepted, because reversing it requires breaking into the vault.

The standard process works as follows. An application sends data and authentication to the tokenization system; if authentication fails, the request is logged for administrators. Otherwise, the system generates a token using random or one-way cryptographic methods and stores it in the vault alongside the original value. The token is returned to the application, which uses it in place of the sensitive data. A small number of trusted applications can detokenize back to the live value when a specific business purpose requires it.

Token generation produces values via one-way functions such as a hash with a strong secret salt, or via random number generation. Token mapping creates a secure cross-reference between token and original value. The token data store holds the pairs, with sensitive values encrypted at rest. Cryptographic key management protects the vault itself.

In payment card contexts, tokenization reduces the scope of systems that touch live cardholder data, which in turn reduces the audit footprint required by the Payment Card Industry Data Security Standard (PCI DSS). The PCI Council defines tokenization as replacing a PAN with a surrogate value, where a third party often holds the link between them; de-tokenization is the reverse, redeeming a token for its PAN. Tokens can be format-preserving, sometimes keeping the last four digits of the original card number, and can be returned to a merchant in authorization responses.

High-value tokens (HVT) act as surrogates that themselves complete transactions, look like real PANs, and can be bound to specific devices, networks, or merchants so that mismatches in geography or hardware flag likely fraud. Multiple HVTs may map to a single card without the cardholder knowing. Low-value tokens (LVT) cannot complete a transaction on their own and only resolve back to a PAN under tight controls, making them useful for back-office systems such as analytics.

First-generation systems mapped live data to tokens through a single database, concentrating every sensitive record behind one vault and forcing continuous data-center synchronization with CAP-theorem trade-offs between consistency, availability, and partition tolerance. Stateless tokenization removes the database dependency, mapping data elements to surrogate values without a shared table while preserving the isolation property. Tokenization is frequently combined with end-to-end encryption so that data is encrypted before entering a low-trust system such as a point-of-sale terminal and only decrypted at the processing host, an approach Heartland Payment Systems pioneered after the 2013 Target breach.

Shift4 Corporation released the technology publicly at a 2005 Las Vegas security summit. Tokenization is now defined or supported across ANSI X9.119 Part 2, PCI Council guidelines, Visa Tokenization Best Practices, and the EMVCo payment tokenization specification (March 2014). EMVCo-based tokenization underpins Apple Pay, Google Wallet, Samsung Pay, and similar mobile wallets, plus secure Visa checkout. Blockchains extend the concept by letting tokens represent ownership of real or intangible assets recorded on tamper-resistant ledgers rather than in a trusted vault, as used by platforms such as eToroX.
